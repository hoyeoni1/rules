# rules

AI 코딩 에이전트(Codex)와 타임박스 웹앱 작업을 할 때 쓰는 개인 작업 규칙.
**이 README만 위에서부터 따라 하면 된다.** 각 단계에 "언제 / 무엇을 / 어떻게"가 있다.

---

## 0. 시작 직후 5분 — 세팅

**언제:** 작업 폴더를 받은 직후, 아무것도 하기 전.

터미널에서 작업 폴더 안에 있는지 확인하고 (`pwd`, `ls`로 요구사항 README가 보이면 맞다) 그대로 붙여 넣는다.
```bash
git clone https://github.com/hoyeoni1/rules ../rules
if [ -f AGENTS.md ]; then cat ../rules/AGENTS.md >> AGENTS.md; else cp ../rules/AGENTS.md .; fi
cp ../rules/PLAN.md ../rules/templates/DESIGN.md ../rules/templates/HANDOFF.md .
git add AGENTS.md PLAN.md DESIGN.md HANDOFF.md && git commit -m "docs: 작업 규칙 · 계획 뼈대"
```
- `../rules`에 못 쓴다고 나오면 → 대신 이걸 쓰고, 아래에서 `../rules`를 전부 `.rules`로 읽는다.
  ```bash
  git clone https://github.com/hoyeoni1/rules .rules && echo ".rules/" >> .git/info/exclude
  ```
- git이 아직 없는 폴더면 먼저 `git init`.
- clone 자체가 안 되면 → 규칙 없이 진행. 아래 "손으로 지키는 3가지"만 지킨다.

**확인:** `ls`에 AGENTS.md · PLAN.md · DESIGN.md · HANDOFF.md가 보이면 끝.

---

## 1. 읽기 (전체 시간의 ~10%)

**언제:** 세팅 직후.

1. 요구사항 README를 **내가 먼저** 한 번 읽는다. 숫자(한도 · 기준)와 "하지 않는 것(범위 제외)"에 표시.
2. Codex에 `PROMPTS.md` **1번(시작)** 을 붙여 넣는다.
3. 결과로 받는 것: PLAN.md 요구사항 체크리스트(R1, R2…), 데이터 요약, "정의 필요" 목록.

**확인:** PLAN.md "요구사항"에 R번호가 채워졌는가. 범위 제외 문장이 들어갔는가.

---

## 2. 요구사항 확인 질문 (~15%)

**언제:** "정의 필요" 목록을 받은 직후. **코드보다 먼저.**

1. "정의 필요" 목록 + `PLAYBOOK.md` 2번 **질문 은행**에서 질문을 고른다. 한 번에 하나, 짧게.
2. 답을 안 주면 **질문 형태를 바꿔** 다시 묻는다. ("알려줘" → "하지 말라고 들은 게 있나?", "불만이 뭔가?")
3. 정답이 없으면 내가 먼저 제안한다: "**이 기준으로 하겠다 — 괜찮나?**" → OK를 받는다.
4. 한도 · 개수 제한이 **없는지**도 확인한다. "없다"도 답이다.
5. 답을 받을 때마다 **바로** 적는다 (Codex 말고 내가):
   - PLAN.md "정의" → `기준: 값`
   - DESIGN.md 3 제약 표 → `| C1 | 내용 | 값 | 담당자 HH:MM |`
   - 충돌하는 조건이 있으면 DESIGN.md 3 "우선순위"

**확인:** 모호했던 항목마다 출처(README / 담당자 HH:MM / 내 가정)가 붙어 있는가.

---

## 3. 설계 (~10%)

**언제:** 핵심 기준이 대부분 정해졌을 때. 다 안 정해졌어도 시간 비율이 넘으면 나머지는 "내 가정"으로 적고 넘어간다.

1. `PROMPTS.md` **2번(설계)** 을 붙여 넣는다.
2. DESIGN.md를 내가 읽고 확인: 구조가 `입력(검증) → 계산(순수 함수) → 저장 → API → 화면`으로 나뉘었나, 알고리즘이 **내가 설명할 수 있는** 방법인가.
3. 결정한 것을 PLAN.md 결정 로그에 한 줄: `[HH:MM] 결정: / 이유: / 버린 대안:`

**확인:** 알고리즘을 소리 내어 3문장으로 설명할 수 있는가. 못 하면 더 단순한 방법으로 바꾼다.

---

## 4. 구현 루프 (~40%) — 기능 하나씩 반복

**언제:** 설계 확정 후. R1부터 하나씩.

한 바퀴:
1. **맡기기** — `PROMPTS.md` **3번**. `<R번호>`, 수정 가능 파일, 제약, 테스트 명령을 채워서.
2. **보고 확인** — Codex 보고 5항목 중 "실패할 수 있는 경우"와 "PLAN에 추가한 줄"을 꼭 읽는다.
3. **설명 받기** — `PROMPTS.md` **5번**. 설명이 이해 안 되면 커밋하지 말고 더 작게 쪼개서 다시 맡긴다.
4. **리뷰** — 두 번째 Codex 세션에 `PROMPTS.md` **4번**. 지적이 맞으면 3번으로 고치게 한다.
5. **기록** — AI가 틀린 걸 잡았으면 PLAN.md "AI 오류"에 한 줄.
6. **커밋** 확인 (`git log --oneline -3`). PLAN.md 체크박스 체크.

이럴 땐:
| 상황 | 할 일 |
|---|---|
| 같은 오류 3번 | 범위를 줄인다. 안 되면 PLAN "한계"에 적고 다음 R로 |
| 새 조건이 떠오름 | 구현 전에 담당자에게 묻고(2단계) 기록부터 |
| Codex가 요구 안 한 기능 추가 | 되돌리게 한다 (`git diff`로 확인) |
| 터미널이 서버 때문에 멈춤 | Ctrl+C 후 "서버는 백그라운드로, 로그는 파일로" 다시 지시 |
| 기록을 한참 못 했음 | `PROMPTS.md` **7번(기록 보정)** |

**확인:** R마다 테스트가 실제로 돌았고 커밋이 있는가.

---

## 5. 검증 · 규모 (~15%)

**언제:** 필수 요구사항(R)이 다 돌아간 뒤. 새 기능보다 이게 먼저.

1. 불변조건 점검 — "누락 0, 한도 초과 0" 같은 전체 결과 규칙을 테스트로 (`PLAYBOOK.md` 5).
2. `PROMPTS.md` **6번(규모)** — ×10, ×100 실행 시간 측정 → HANDOFF 성능 표.
3. 담당자가 말한 불만이 실제로 줄었는지 전/후 숫자 하나.

**확인:** PLAN.md "검증"에 테스트 기대값 출처와 측정 숫자(n, 시간)가 있는가.

---

## 6. 마무리 (마지막 ~10%) — 새 기능 금지

**언제:** 남은 시간이 전체의 10%가 되는 순간. 하던 기능이 있어도 멈춘다.

1. 실행 확인 — PLAN.md "실행 방법" 명령을 그대로 쳐서 실제로 뜨는지.
2. `PROMPTS.md` **8번** — HANDOFF.md 채우기. "요청 하나 따라가기" 표가 꼭 있어야 한다.
3. `QA.md` **"마무리 전 15분 — 질문 리허설"** 프롬프트를 리뷰 세션에 붙여 넣는다 → 나온 질문에 **내가** 4문장으로 답해 본다. 막히는 곳은 5분 안에 고치거나 "한계"에 적는다.
4. `QA.md` **1장 요약**을 채우고 한 번 읽는다. 숫자(테스트 수, n, 시간)는 외운다.
5. 마지막 커밋 → `git status`가 깨끗한지.

---

## 7. 작업 직후 질문에 답할 때

- 모든 답: **결론 → 근거(출처) → 검증(실제로 한 것) → 한계 1줄**
- 질문 유형별 재료 위치: `QA.md` 표 (Q1 구조 · Q2 알고리즘 · Q3 요구 해석 · Q4 예외 · Q5 검증 · Q6 규모 · Q7 AI 오류 · Q8 트레이드오프)
- 질문 전제가 내가 만든 것과 다르면 그 차이부터 한 문장.
- "AI가 그렇게 짰다" 금지 — **내가 왜 받아들였는지**를 말한다.

---

## 손으로 지키는 3가지 (규칙을 못 가져와도 이것만은)
1. **결정할 때마다 PLAN.md에 한 줄** — 결정 / 이유 / 버린 대안. 합의는 상대 · 시각까지.
2. **AI가 틀린 것 최소 2건 기록** — 무엇이 / 어떻게 발견 / 어떻게 수정.
3. **"해줘" 한 줄로 맡기지 않는다** — 범위 · 제약 · 완료 기준(테스트 명령)을 같이 주고, 설명을 듣고 이해한 것만 커밋.

## 하지 않는 것
요구에 없는 기능 · 옵션 남발(1~2개까지) · 세션 3개 이상 · 요구 없는 Docker나 복잡한 솔버 · 측정 안 한 성능 숫자 말하기.
